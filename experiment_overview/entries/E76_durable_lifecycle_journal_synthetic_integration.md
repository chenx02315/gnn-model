# E76：持久账本与清理验收协议的本地串联通过

日期：2026-10-21。承接 E75 的真实 Linux 三场景结果，用户要求继续。

## 先说结论

已完成新账本的本地实现、八类故障串联和确定性复跑。它解决的是：**一项调用从准备启动到清理完成，在哪一步写账、什么时候才能宣布费用完整。**

E76新增后端都是进程内模拟对象，新增八类fixture没有真实子进程；没有再连接 A/B或创建容器。完整回归仍包含旧 E66 等模块原有的微型本地 Python 子进程测试，这些不计作本次新增fixture、Linux联跑或ATPG调用。**E75 已真实验证过 Linux 清理机制，E76 验证了账本接入协议，但二者尚未在一个真实 Linux runner 中联跑。** 不能把两项分别通过拼成“真实 ATPG runner 已认证”。

## 为何新建 v2，不改旧账本

旧 E65 账本的费用节点要求 `ATOMIC_ATPG_PROCESS_ONLY`，并保留原来的不完整下界语义。新串联区间包含日志写入、启动、等待和清理，不能默默塞进同一个“纯 ATPG 时间”字段。因此新建 `prospective_lifecycle_journal_v2.py`，保留旧代码和历史数据不变。

起点由协调器在写 INTENT 前采样；只有该行写入及 fsync 确认后才调用后端。拿到身份后，LAUNCHED 也需确认；清理确认后、终态日志写入前采终点。整个区间包含 INTENT 和身份日志确认、启动、等待、清理；不包含终态日志确认。但**终态确认仍是发布完整费用的必要条件**。

例如本次固定假时钟给三个正常验收场景各100单位，成功、预期失败和超时都要计入，合计300。这个300是测试输入，不是实测纳秒耗时，更不是 ATPG 加速结果。任一项不确定，整个可用总和为 `null`，不填0，也不只保留成功项。

## 八类串联结果

| 案例 | 模拟启动调用 | 清理调用 | 实时完整费用 |
|---|---:|---:|---|
| 成功、预期失败、超时三个场景均完整 | 3 | 3 | 固定假时钟300 |
| INTENT 持久化确认失败 | 0 | 0 | null |
| 启动抛错、没有可靠句柄 | 1 | 0 | null，阻止后续项 |
| 启动返回空句柄，但附带合法身份 | 1 | 0 | null，不进入等待/清理或下一项 |
| 等待/后端结果发生异常 | 1 | 1 | null |
| 清理后仍报告残留进程组 | 1 | 1 | null |
| 取消类 BaseException | 1 | 1 | null，异常继续传播 |
| 终态整行写完但 fsync 确认失败 | 1 | 1 | null |

表中“启动/清理调用”只是模拟对象的方法调用，实际操作系统进程数为0。所有故障后再试下一项，都在调用后端前被拒绝。

最后一行尤其重要：完整字节可能通过哈希链和结构回放，但它不能证明此前 fsync 已返回成功。因此回放只给结构状态和链头，不恢复可用费用。正常案例回放也不会冒充实时写入确认。

## 独立复核发现并修复的问题

初版把后端返回的可变身份字典直接保存在实时状态中。后端如果随后修改同一个对象，实时状态会跟着变化，可能显示完整，而磁盘回放拒绝身份不一致。已在拿到句柄后的清理保护区内校验并复制身份，append 入口也深复制调用方内容；嵌套对象及返回事件的修改均不能污染已确认状态。

另补空日志不发布0费用、跨项时钟屏障、文件外部变化后停止发布费用、关闭/写入不确定后停止、单 worker 嵌套启动拒绝，以及主异常与清理异常同时保留。明确输出 `synthetic_only=true`、`os_authenticated=false`、`actual_processes=0`；这些标签本身不是安全沙箱或内核认证。

收尾又发现：`launch`返回`None`句柄时，合法的身份字典不能替代真实句柄。现将其保持为未知启动，封锁writer，不调用等待、`cleanup(None)`或下一项；新增单测和独立串联案例。初版和中间版的验收记录保留，不拿早期24项/七类案例作为最终版本验收。
